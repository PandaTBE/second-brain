# План развития Second Brain для Codex и Claude

Статус: реализация в работе; этапы 0–1 и 3 завершены, код этапов 2 и 4 реализован
и проверен. Приёмка настоящих embeddings ожидает локальную модель; несколько
дополнительных GUI-проверок этапа 4 — ручную разблокировку Mac. Следующий — этап 5.
Дата: 2026-11-06. Репозиторий: `second-brain`.
Исходная точка на момент подготовки: ветка `codex/apple-notes-outlook`, коммит `7fe1f49`.

## Задача

Сделать существующую память полезнее для агентов: находить сведения по смыслу,
передавать ограниченный контекст с проверяемыми доказательствами, различать
повторяющиеся факты и изменения решений. Добавить управление приватностью,
быстрый поиск из macOS и восстановление базы.

Это план исполнения, а не описание уже доступных возможностей. В новом чате
сначала проверить фактическое состояние Git и кода: оно могло измениться.

## Что уже существует

- Нативное приложение SwiftUI/AppKit, FastAPI на loopback, SQLite с FTS5/BM25.
- Импорт сессий Codex/Claude/Qwen, папок, Notion, GitHub, Gmail/Яндекс Почты,
  Apple Notes и Outlook. Последние два источника пока только в локальных исходниках.
- Карточки через облачную модель или локальную Ollama, очередь, повторы, паузы,
  контроль ревизий и единый писатель.
- Отдельный stdio MCP с четырьмя инструментами: `search_memory`, `get_record`,
  `get_context_brief`, `get_sync_status`. MCP может работать без приложения.
- Поиск сейчас лексический. `get_context_brief()` возвращает до восьми записей
  без аргумента запроса. База хранит текущую ревизию, а не полную историю текстов.
- Исходные материалы помечаются недоверенными; цитаты карточек проверяются.
- Локальный граф и история, публичная документация EN/RU, переносимая сборка.

Последняя полная проверка перед планированием: 1193 Python-теста, покрытие 91,19%,
29 CoreChecks и 29 Node-проверок. Это ориентир, а не замена проверкам нового кода.

## Порядок и результат этапов

| Этап | Результат | Польза агенту |
| --- | --- | --- |
| 0 | Проверки качества поиска и контракты | Изменения оцениваются по воспроизводимым запросам |
| 1 | Политики источников и миграции | Агент получает только разрешённые сведения |
| 2 | Локальный семантический и гибридный поиск | Находит переформулированные вопросы и синонимы |
| 3 | Контекст с доказательствами через MCP | Даёт ответы с цитатами и тратит меньше контекста |
| 4 | Факты, дубли и история решений | Различает актуальное, прошлое и противоречивое |
| 5 | Быстрый нативный поиск | Пользователь быстрее находит и передаёт контекст |
| 6 | Резервные копии и восстановление | Память можно восстановить и перенести |

Реализовывать последовательно, отдельными проверяемыми изменениями.
Первый полезный рубеж — завершённые этапы 0–3. Второй — этап 4.
Этапы 5–6 входят в общий объём, но не должны задерживать проверку первых результатов.

## Общие ограничения

1. Сохранить SQLite как основное хранилище, FTS5/BM25 и существующие источники.
   Не вводить отдельный сервер векторной базы без измеренной необходимости.
2. Сохранить имена, обязательные аргументы и основные поля четырёх MCP-инструментов.
   Новые параметры — необязательные; новые инструменты — только чтение.
3. Обычное чтение памяти не должно скрыто вызывать платную LLM. Ответы агента
   формирует сам Codex/Claude; Second Brain предоставляет доказательства.
4. Локальные embeddings — отдельная настройка и отдельная embedding-модель.
   Модель карточек Qwen/Ollama не обязательно умеет создавать embeddings.
5. Не запускать автоматическую загрузку весов, регистрацию аккаунтов или внешнюю
   обработку личных данных в процессе разработки. Для тестов — временная база и фейки.
6. Сохранить ревизии, tombstone удалённых источников, паузы, writer lease,
   ограничения размера запросов/ответов и существующую сетевую политику.
7. Результаты из источников остаются данными: инструкции внутри них не исполняются.
8. Не менять опубликованный тег и ZIP `v0.1.0`. Публикация нового выпуска — отдельное действие.

## Этап 0. Проверки качества и технические контракты

- Изучить текущие точки входа, миграции, запросы поиска и жизненный цикл MCP.
- Создать синтетический корпус на русском и английском: не менее 40 запросов
  с ожидаемыми документами, точными терминами, пересказами, отрицательными
  примерами, конфликтующими решениями, датами и разными источниками.
- Добавить набор большего размера для измерения времени и памяти. Не использовать
  реальные сессии, почту, Notes или содержимое `.data`.
- Зафиксировать исходные Recall@5, MRR@10, долю повторов в выдаче и p50/p95 времени.
- Отдельно измерять поиск по готовому вектору, создание вектора запроса и холодный
  запуск модели; не смешивать их в одно обещание скорости.
- Описать контракт поискового результата и пакета доказательств до изменения API.

Готово, когда benchmark запускается одной командой, не ходит во внешнюю сеть
и показывает исходные результаты BM25. Первичные цели для этапа 2:
Recall@5 на переформулированных запросах лучше исходного минимум на 15 процентных
пунктов, без снижения MRR@10 на наборе точных терминов. Если цель не достигнута,
показать результаты и доработать ранжирование, не объявлять улучшение на глаз.

## Этап 1. Политики источников и совместимые миграции

### Раздельные разрешения

В настройках каждого источника независимо задать:

- разрешение импорта новых материалов;
- видимость в нативном локальном поиске;
- видимость через MCP;
- разрешение локальной модельной обработки;
- разрешение внешней модельной обработки: карточки и будущие операции генерации.

Флаг «обрабатывать локально» не означает «не передавать агенту».
Облачный Codex/Claude получает текст, возвращённый MCP. Поэтому видимость MCP
должна управляться отдельно, без обещания различать локального и облачного клиента
по недостоверному имени приложения. Ограничения на отдельные MCP-клиенты
не входят в первый вариант: для них нужна проверяемая идентичность.

### Поведение

- Мигрировать старые настройки с сохранением фактического поведения: импорт
  и видимость существующих источников не отключаются неожиданно; новые платные
  операции не включаются. Поведение defaults явно описать и покрыть тестами.
- Централизовать проверку политики. Применять её до ранжирования/формирования
  выдачи, прямого чтения по ID, сводок, истории, графа и статистики MCP.
- Проверять актуальную политику перед допуском модельного запроса и перед записью
  его результата. Не обещать отменить передачу, уже состоявшуюся до изменения флага.
- Отмена внешней обработки не удаляет локальную память. Изменение политики
  не должно позволять старому MCP-процессу продолжать возвращать скрытые материалы.
- Добавить исключения для локальных путей и выбранных папок Notes; показывать,
  что будет исключено. Для остальных коннекторов использовать их реальные области
  выбора; не обещать фильтрацию, которой API источника не предоставляет.
- При исключении уже импортированного материала убрать его из активного поиска,
  MCP и производных индексов; не трогать оригинал. Показать пользователю последствия.

Готово, когда закрытый источник нельзя получить ни через поиск, ни через
`get_record`, `get_context_brief`, статистику или новый инструмент доказательств,
включая два одновременно работающих MCP-процесса и изменение политики во время задания.

## Этап 2. Локальные embeddings и гибридный поиск

### Индексация

- Расширить существующий фиксированный loopback-адаптер Ollama для embeddings,
  сохранив запрет облачного fallback. Поддержать ограниченные пакеты и явную
  обработку слишком длинного ввода; не полагаться на незаметное усечение текста.
- Дать выбрать установленную embedding-модель в нативных настройках. Проверять
  её пригодность, размерность и локальный режим. Если модели нет, объяснить,
  как её установить; не подменять её моделью карточек.
- Хранить в SQLite векторы и идентичность индекса: материал, ревизия, хеш текста,
  модель/версия либо digest, размерность, версия подготовки текста и состояние задания.
- При смене модели создать новую генерацию индекса. Не сравнивать векторы разных
  моделей/размерностей и не выдавать старую ревизию после изменения текста.
- Индексировать в фоне с продолжением, лимитами, паузой и контролем нагрузки.
  Удаление/исключение источника блокирует поздние записи векторов.
- Пока индекс строится, готовые материалы доступны, остальные находятся через BM25.

### Поиск

- Выполнять независимое получение кандидатов BM25 и семантического поиска по всем
  разрешённым материалам. Поиск векторов только среди лексических совпадений
  не решает задачу поиска без общих слов.
- Объединять списки через ранговое слияние, например RRF; коэффициенты закрепить
  benchmark. Не складывать напрямую несопоставимые BM25 и cosine scores.
- Добавить режимы `lexical`, `semantic`, `hybrid` и явную диагностику фактически
  использованного режима. При недоступной Ollama сохранить рабочий BM25 без
  скрытого сетевого вызова и без длительной блокировки MCP.
- Одинаково обслуживать HTTP и stdio MCP. Создание вектора запроса может обращаться
  к явно включённой локальной модели; запись индекса принадлежит фоновому писателю,
  а не каждому MCP-процессу. Учитывать работу MCP при закрытом приложении.
- Начать с изолированного интерфейса векторного хранилища внутри SQLite.
  Выбрать точный поиск или расширение после измерений на целевом Mac и проверки
  упаковки arm64. Не загружать произвольные SQLite extensions из пользовательских путей.

Готово: цели этапа 0 выполнены; все результаты соблюдают политики; нет устаревших
векторов в выдаче; повторная индексация идемпотентна; нет зависания при недоступной
модели. Зафиксировать p95 на 10 000 материалов и потребление памяти на конкретном
оборудовании; выбранное решение должно читать данные ограниченными порциями.

## Этап 3. Пакет доказательств и ответы с источниками

- Добавить read-only MCP-инструмент `get_evidence_bundle` с запросом, необязательными
  фильтрами источника/проекта/дат и ограниченным бюджетом контекста.
- Не превращать существующий `get_context_brief()` в несовместимый query-метод.
  Старые вызовы должны продолжать работать.
- Возвращать стабильные citation IDs, ID материала/источника, ревизию, даты,
  заголовок, исходный URI/идентификатор, точную цитату и контекст вокруг неё.
  Смещения относятся к сохранённому нормализованному тексту, а не к байтам оригинала.
- Убирать повторяющиеся фрагменты, ограничивать длину, распределять бюджет между
  несколькими релевантными источниками. Не выдавать оценку ранжирования за вероятность истины.
- Если данных мало — вернуть неполноту/пустой результат. Различать даты сообщения,
  изменения источника и импорта; недатированный материал не получает вымышленную дату.
- Агент составляет ответ своей моделью и ссылается на citation IDs. Добавить
  краткие рекомендации использования в MCP description и EN/RU user guide.
  Не дописывать глобальные инструкции Codex/Claude без отдельного запроса.
- В приложении добавить просмотр найденных доказательств и копирование контекста.
  Для поддерживаемых URI — безопасное открытие оригинала; для opaque Notes ID —
  показ идентификатора без выдуманного deep link.
- Если в приложении добавляется кнопка «Спросить память», генерация запускается
  только явным действием с выбранным провайдером и проверкой политик. Этот UI
  не является условием готовности MCP-пакета и не должен добавлять скрытые расходы.

Готово: Codex и Claude получают один и тот же пакет из одной базы; каждая цитата
проверяется по тексту и ревизии; исключённые/удалённые материалы не возвращаются;
пустой поиск не создаёт выдуманный ответ; вредоносный текст источника остаётся данными.

## Этап 4. Факты, дубли и история решений

- Ввести производные сущности факта/решения с доказательствами. Материалы и их
  происхождение сохраняются; похожие тексты не удаляются ради объединения карточек.
- Точные дубли объединять детерминированно. Семантическое сходство использовать
  как предложение группы, а не как доказательство равенства или противоречия.
- Для извлечения фактов использовать существующую очередь карточек с версиями
  промпта/схемы, точными цитатами, бюджетом попыток и политиками источника.
- Различать «подтверждено источником», «кандидат», «возможный конфликт» и явное
  «заменяет предыдущее». Более поздняя дата сама по себе не отменяет старое решение.
- Для истории сохранять изменения решений с доказательствами начиная с включения
  новой функции. Не обещать восстановить прошлые версии, которых нет в базе.
- При обновлении текста перепроверять доказательства. Потерявшие подтверждение
  факты не выдавать как актуальные. При удалении источника убрать его доказательства;
  производные данные без оставшихся разрешённых подтверждений скрыть/удалить.
- Добавить просмотр истории в приложении и чтение через пакет доказательств
  либо отдельный read-only инструмент. Показывать конфликты, а не молча выбирать ответ.

Готово: одинаковый факт из трёх источников занимает одно место в выдаче и имеет
три подтверждения; разные решения остаются различимы; смена ревизии, политики
и удаление любого источника не оставляют недействующих подтверждений.

## Этап 5. Быстрый поиск macOS

- Нативная панель по настраиваемой глобальной горячей клавише, работающая из строки меню.
- Debounce, отмена устаревших запросов, управление клавиатурой, доступность VoiceOver,
  понятные состояния загрузки/нет результатов/сервис остановлен.
- Те же результаты и политики, что в основном поиске: источник, дата, фрагмент,
  открытие материала и копирование контекста с цитатами.
- Проверить конфликт сочетаний. Не добавлять доступ к записи клавиатуры или
  Accessibility-разрешение, если выбранный механизм сочетания его не требует.
- Не копировать текст в буфер обмена до явного действия пользователя.

Готово: вызвать панель из другого приложения, найти материал, выбрать стрелками,
скопировать контекст или открыть материал, закрыть Esc. Задержанный ответ старого
запроса не заменяет новый. При закрытом окне основное приложение продолжает работать.

## Этап 6. Резервные копии, перенос и восстановление

- Делать согласованный снимок SQLite через штатный Backup API, а не копировать
  один открытый `.sqlite` без учёта WAL. Конфигурацию и политики включать в
  согласованный manifest со схемой, версией приложения и контрольными суммами.
- Предусмотреть ручное создание и опциональное расписание локальных копий
  с ограничением числа/объёма и понятной ошибкой при нехватке места.
- Для переносимого приватного архива использовать поддерживаемое шифрование
  проверенной библиотеки; не разрабатывать собственный криптоформат. Проверить
  восстановление на другом Mac по паролю/ключу, не зависящему только от старого Keychain.
- Не экспортировать API/OAuth/почтовые секреты из Keychain. После переноса
  соединения требуют нового входа; старые пути и Notes folder IDs не активировать
  на другом Mac без проверки и явного выбора пользователя.
- Отметить, что копия может содержать материалы, позднее удалённые из рабочей базы.
  Управление старыми копиями должно быть явным.
- Восстановление: проверка архива, безопасная распаковка без traversal/symlinks,
  ограничения размера, проверка схемы и целостности, предварительный снимок текущего
  состояния, транзакционно управляемая замена и откат при ошибке.
- Учесть независимые MCP-процессы и открытые SQLite/WAL: ввести согласованный режим
  обслуживания для поддерживаемых процессов. Если старые процессы нельзя безопасно
  остановить/изолировать, восстановление должно потребовать их закрытия, а не
  заменять базу под работающими читателями. Не завершать чужие процессы автоматически.
- После восстановления возобновлять импорт/модельные задания только по безопасному
  состоянию; не запускать оплаченную очередь автоматически из импортированного архива.

Готово: восстановленная временная база даёт те же разрешённые результаты и цитаты;
повреждённый архив, неверный пароль и прерванное восстановление не портят рабочую
базу; архив не содержит Keychain-секретов; проверен сценарий двух MCP-клиентов.

## Общая готовность и рабочий процесс

- Для каждого этапа: тесты поведения → реализация → review → целевые проверки.
  Использовать предусмотренных AGENTS.md специалистов, включая security и retrieval review.
- Миграции проверить на копиях старых синтетических схем, при двух процессах,
  отмене, паузе, удалении и повторном запуске после прерывания.
- Проверки: Ruff; Python с покрытием не ниже 80%; Node для изменённого JS;
  `swift run --package-path native SecondBrainCoreChecks`; полный native build.
- Новые критические пользовательские сценарии проверить в изолированной нативной
  сборке. Не подменять её тестированием только HTML-страницы.
- Проверить frozen helper и включение новых ресурсов/зависимостей в portable arm64 app.
- Обновлять README, EN/RU guides, архитектуру, безопасность и Unreleased changelog
  по фактически реализованному поведению. Не обещать шифрование/семантику до проверки.
- Перед публикацией проверить точный Git index на секреты и личные пути. В этой
  задаче не публиковать репозиторий, ветки, ZIP или релиз без отдельного запроса.
- В конце каждого этапа фиксировать в этом плане статус, коммит, команды проверок,
  результаты benchmark и оставшиеся ограничения. Не отмечать этап завершённым
  только потому, что его интерфейс нарисован.
